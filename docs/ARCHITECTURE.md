# 架构与正确性边界

```mermaid
flowchart LR
  A[服务日班次 JSON / typed API] --> B[引用与时序验证]
  G[GTFS 静态子集] --> H[Python 日期/CSV 适配]
  H --> A
  B --> C[站点出发与接驳索引]
  C --> D[stop/boardings 下的 arrival/walk 标签前沿]
  D --> E[完整行程与来源停站索引]
  E --> F[MoonBit 可行性重放]
  E --> I[CLI / 本地浏览器]
```

搜索采用有限标签校正，不是 RAPTOR 的移植。每个标签包含位置、到达时间、上车次数、累计接驳用时及不可变父指针。相同 `(stop,boardings)` 上，若已有标签更早或同时到达且接驳不多，新标签可删除：它之后能赶上的每个固定班次，旧标签都能通过等候赶上，且消耗资源不大于它。

不同上车次数分开保存，因而不会把“早到、多换乘”直接覆盖“晚到、少换乘”。终点对三个目标统一支配筛选；同分只保留一条确定性见证。由目的地继续旅行不可能改善到达时间/上车次数/接驳三项，故可停止扩展该标签。

从一次合法上车枚举同一 trip 后续可下客的停站，直通不在中途重新收取 boarding 或缓冲；发车时刻、上/下客、无障碍和整体延误均直接取自已验证事实。站点出发索引不假定最早发车一定最早到达，超车班次仍会参与。

算法是资源有界的。标签数与候选工作计数达到上限后抛出错误，丢弃整个未完成结果；不输出伪装完整的截断前沿。索引构建和验证也有静态容量上限，但工作计数不是总 CPU/内存上限，恶意任务仍需宿主隔离。

输入含可变数组，但同步求解不修改它，也不保留可由外部操纵的长生命周期状态。结果见证为新数组；scenario 对 trip.calls 做分离复制。源码的 private Search/Label 不对外暴露。GTFS 与 JSON 层负责不同边界，不把适配器限制藏进路由算法的正确性声明。

规模不适合直接与全国级、预处理、SIMD 或高度优化的 RAPTOR 实现比较。当前选择优先保证小中型模型的完整三目标标签、清楚语义和可穷举验证；下一阶段应以真实、经授权的 feed、性能分布及实际应用集成决定优化路线。
